# codex レビュー依頼プロトコル

codex（チーム `investigelion` の別エージェント・OpenAI Codex 拡張）にレビューを依頼するときは、**必ず以下の5観点を明示して渡す**。ユーザーから 2026-06-01 に明示された依頼フォーマット。

## なぜこの Skill があるか

「動いた」「テスト通った」だけのレビューは浅い。codex には**システムゴールとの整合・欺瞞防止・純利益のある改善・リスクの否定**まで踏み込ませる。単一エージェント（claude）の見落とし・自己正当化を、独立エージェントの敵対的視点で潰すのが目的。

## 渡すときに必ず含める5観点

codex へのメッセージに、以下を**明示的な問い**として入れる：

1. **システムゴール適合**：この変更/設計は INVESTIGELION のゴール（¥10万から段階的に大規模化・中期で利益・中小型成長株ピック・実運用で問題ない仕様・最終的に自動売買）に即しているか。ズレていれば指摘。
2. **タスクゴール準拠**：今回のタスクのゴールは、上位のシステムゴールに準拠しているか。タスク単体では正しくても全体目的から外れていないか。
3. **ハルシネーション/欺瞞の検査**：推測で事実を作っていないか。「動いてる」を装う欺瞞（ノード success だけ・閾値が永遠に発火しない・実績ゼロを隠す等）が起きないか。コード/DB/実データで裏が取れるか。
4. **ブラッシュアップ・アップグレード提案**：より強固にする改善・格上げがあれば提案（純利益が正のものだけ。思いつき全部出しは禁止）。
5. **リスクがある場合は否定**：リスクが純利益を上回るなら、賛成せず**明確に否定**する。賛成・要約・追従で終わらせない。

## 渡し方（手順）

1. レビュー対象を簡潔に要約（何を・なぜ・どう変えたか。working tree の変更範囲を明示し、無関係な既存差分は「無視して」と伝える）。
2. **コスト制約を明記**：構築期間中は実バッチ/LLM 実行禁止。「コスト0の静的検証/DB突合/単体テストのみ」と指示（[[feedback_no_batch_during_construction]] / [[feedback_api_cost_disclosure]]）。
3. 再現コマンド（grep / pytest / sqlite 集計）を添えて、codex が独立に裏取りできるようにする。
4. 上記5観点を**番号付きの問い**として末尾に置く。
5. 送信：
   ```
   /shot send codex "<上記を含むメッセージ>"
   ```
   またはスクリプト直叩き：
   `~/.agents/skills/shot/scripts/send.sh investigelion shot codex "<message>"`
6. **monitor を立てておく**（delivery mode off のことが多い）。codex の返信を取りこぼさないよう、inbox をポーリングする Monitor を稼働させる。
7. 返信が来たら：一致点＝確度確定、相違点＝実コードで裁定、codex 独自指摘＝見落としとして取り込む。**翻意の根拠は必ずコード/データで示す**（[[feedback_check_memory_first]]）。

## テンプレート

```
【<対象> レビュー依頼】<1-2行サマリ>。コスト0の静的検証/焦点テストのみで。
<変更点を箇条書き。working tree の無関係差分は無視と明記>
<再現コマンド>

[レビュー観点]
1) システムゴール適合: <この変更はゴール（¥10万→スケール/中期利益/成長株/実運用品質/自動売買）に即すか>
2) タスクゴール準拠: <今回のタスクゴールはシステムゴールに準拠か>
3) ハルシネーション/欺瞞: <推測で事実を作ってないか・「動いてる」欺瞞が無いか・データで裏が取れるか>
4) 改善提案: <純利益が正のブラッシュアップ/アップグレードがあれば>
5) リスク否定: <リスクが純益を上回るなら明確に否定して>
```

## やってはいけない

- ❌ 5観点を省いて「これ見て」だけ投げる
- ❌ 実バッチ/LLM 実行を codex に依頼する（コスト発生）
- ❌ codex が賛成しただけで「OK」と進める（賛成の根拠とリスク評価まで確認）
- ❌ codex の指摘を裏取りせず鵜呑み／逆に裏取りせず却下する
