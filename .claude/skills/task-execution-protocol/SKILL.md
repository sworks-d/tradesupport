# タスク実行プロトコル

ユーザーがタスク指示を出したら、**実装に直入りせず**、必ず以下の 4 ステップで進めること。

## なぜこの Skill があるか

ユーザーから何度も明示的に指示されている：
- 「タスクとして整理して、マイルストーンを置いた実行リストを作成して」
- 「パイプラインの断絶、無駄なデータ作成、データの授受、無駄のない収集がないか必ずチェック」
- 「タスクのマイルストーンごとにハルシネーションチェック」

これが守れずに実装直入り → 後で断絶・無駄・ハルシネーションが見つかって修正の往復になる。同じ失敗を繰り返さないため。

## 4 ステップ + Step 0

### Step 0a: 指示の意図を読む + 付加提案（最優先）

ユーザー指示は 100 点ではない。表層を実装するな。以下を必ず：

1. **表面の要求**: ユーザーが書いた内容
2. **裏の意図**: なぜそれを求めているか
3. **抜けてる視点**: 全体目的から見て指示が触れていない改善点
4. **付加提案候補**: 強固にする追加施策の **候補**

**付加提案する前に必ず自己レビュー**: 候補が出たら、ユーザーに出す前に **内部処理で**「目標と照らして客観論理でメリット・デメリットを検証 → 純利益が明確に正のものだけ提案」する。思いつきの全部出しは禁止。詳細: [[feedback_proposal_self_review]]

参照: [[feedback_proactive_enhancement]], [[feedback_proposal_self_review]]

### Step 0b: 自走 / 確認の見極め（実装前）

| 自走 OK | 確認必須 |
|---|---|
| 純粋アップグレード（既存挙動への影響なし） | 既存挙動の変更 |
| コスト ¥0、リスクなし | API コスト発生 |
| 既存設計指針の自然な延長 | 設計判断（アーキテクチャ変更） |
| 全体目的への明らかな貢献 | ユーザー過去発言との矛盾可能性 / 致命候補修正 / 独自 DB 書き換え |

自走中も区切りで進捗報告。長時間沈黙作業禁止。

### Step 0: 目的 + 全体ゴール貢献の確認（最優先・実装前）

タスク指示を受けたら **最初に** 必ず以下を提示：

```
## このタスクの目的
<ユーザー指示の根本的な狙い>

## 全体ゴールへの貢献
<INVESTIGELION の目的 (少額〜大規模スケール / 成長銘柄ピック / 実運用品質 / 自動売買移行) のどこに効くか>

## 代替手段の検討
<より目的に直接的な手段はないか / 既存実装で足りないか>

## このまま進めて良いか
<目的・代替手段を考慮した上での推奨アクション>
```

ユーザー承認を得てから Step 1 へ。「言われたから」で直入りは禁止。

参照: [[feedback_task_purpose_check]]

### Step 1: タスク分解 + マイルストーン設計（実装前）

ユーザー指示を受けたら、必ず以下のフォーマットを **テキスト** で提示してから着手：

```
## タスク
<ユーザー指示の要約>

## マイルストーン
M1. <小タスク 1>
    完了条件: <何が出来たら完了か>
    所要: ~Xh
M2. <小タスク 2>
    完了条件: ...
    所要: ~Yh
...

## 依存関係
M1 → M2 → M3（順次）or M1 / M2 並列、など

## 全体所要
~Zh
```

並行で `TodoWrite` に同じ内容を入れる。

### Step 1.5: API・LLM コスト試算（実行前）

タスクが API / LLM / ネットワーク呼び出しを伴う場合、**実行前に必ず**金額目処を提示：

```
🔔 これから実行する処理のコスト試算:

API 種別     : <Anthropic Haiku / yfinance / J-Quants 等>
呼び出し回数  : <N 回見込み>
想定コスト   : ¥<最小>〜¥<最大>
所要時間     : <X 分〜Y 分>
失敗時       : <再試行コスト等>

実行してよいですか？
```

ユーザー承認なしで実行しない。**請求はユーザーに届く**ことを忘れない。詳細は [[feedback_api_cost_disclosure]] を参照。

### Step 2: パイプライン無駄チェック（実装前）

各マイルストーンについて以下を確認し、問題があれば設計を見直す：

| 確認項目 | 内容 |
|---|---|
| **断絶** | データが途中で消える経路はないか（取得した値が使われずに破棄、変換途中で null 化 等） |
| **無駄なデータ作成** | 既存データで代替できないか。新規ファイル / DB レコードは本当に必要か |
| **無駄な授受** | 関数間の引数・戻り値が冗長でないか。不要な変換 / コピー |
| **無駄な収集** | 既存 API / DB / キャッシュで取れる情報を再収集していないか（yfinance, J-Quants, LLM の呼び出し重複） |

無駄が見つかったら **実装前に設計を直す**。実装後の手戻りは高コスト。

### Step 3: マイルストーンごとに実装

1 マイルストーンずつ実装。次に進む前に **そのマイルストーンの完了条件を満たしたか** を確認。

### Step 4: マイルストーンごとにハルシネーション検証

各マイルストーン完了時に、必ず以下を検証する：

- [ ] **データ存在性**: 必要データが実 DB / 外部 API に存在するか確認した
- [ ] **取得失敗時の挙動**: 価格 None・API 失敗時に「推測しない」設計か（既知ハルシネーション防壁 H4, H10）
- [ ] **既存防壁との整合**: 11 ハルシネーション防壁（H1-H11）を破っていないか
- [ ] **テスト追加**: ロジック変更に対応するテストを書いたか
- [ ] **全テスト回帰**: 既存テスト 793 件が落ちていないか
- [ ] **新規データの正当性**: 新規生成データ（snapshot / report 等）の値が「実 DB と整合しているか」を spot check

全項目クリアしないと次のマイルストーンに進まない。

## ハルシネーション防壁 11 件（既存・参考）

H1: Universe 不存在を弾く / H2: 上場廃止 (is_active=False) を弾く / H3: 仮想 ticker を弾く / H4: yfinance 価格不在で取引しない / H5: J-Quants 失敗で credibility スキップ / H6: EDINET 開示反映 / H7: 信用性 S5 (MELCHIOR 反証) / H8: 予算超過で fill しない / H9: 重複 Decision 防止 / H10: 推測しない (None 返り値で進めない) / H11: broker_provider≠moomoo で moomoo OpenD 呼ばない

## やってはいけない

- ❌ 整理なしで実装に直入り
- ❌ マイルストーン未設定のまま長時間作業（迷子になる）
- ❌ パイプライン整合性を確認せず新規ファイル / 関数を追加
- ❌ マイルストーン完了時のハルシネーション検証を省略
- ❌ 「動いたから OK」で次に進む（防壁を破ってる可能性）
- ❌ TodoWrite を使わず脳内追跡（ユーザーから状況が見えない）
