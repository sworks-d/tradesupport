# Trading Agent — MAGI独立検証層 要件定義書（code向け）

作成日：2026-05-22
位置づけ：既存システム（Phase 1.4 まで実装済み）に、**ユーザーのジャッジ直前の独立検証機関としてMAGIを挿入する**ための要件。codeはこれを元に設計・実装をブラッシュアップする。

---

## 0. 最重要の前提（取り違え厳禁）

**MAGIは既存の処理層を一切置き換えない。**

既存の各エージェント（screening-agent / market-analyst / sell-recommender / portfolio-builder / manual-input-analyst / topics-collector）が分析・推奨を出すフローは**そのまま無改変**。

MAGIは、それらの出力と**ユーザーの最終ジャッジ（決裁）の間に、独立した検証機関として1段挿入される**。

```
[既存] 各エージェントが分析・推奨を生成
            │   ← ここまで一切変えない
            ▼
[新規] MAGI 独立検証機関 ★ジャッジ直前に挿入
            │     3審判（独立検証）→ 防御層 → 統合機構 → 碇司令
            ▼
[既存] ユーザーが決裁（承認/否認/保留）→ Tier 1 手動発注
```

- MAGIは「分析をやり直す」のではない。既存の分析・推奨を**鵜呑みにせず、決裁の直前に独立検証する関所**。
- 3審判は互いを見ず、独立に可否を出す。割れたら「割れた」と出す。統合して1点にしない。
- 既存の `architecture.html` の構造（外部データ→FastAPI→Orchestrator→MCP→DB→LLM→UI）は無改変。その後段に検証ゲートが増えるだけ。

## 1. MAGIを挿入する正確な位置（既存DAGとの関係）

既存の朝バッチDAG（ORCHESTRATION.md §2.1）は次の順：

```
pre_check → topics-collector / universe_refresh → screening-agent
  → market-analyst × N（並列）   ← 既存：買い候補の分析・推奨を生成
  → sell-recommender              ← 既存：保有の利確/損切り推奨を生成
  → portfolio-builder(review)
  → link_topics_decisions → summary_generator → health_report → notification → END
```

**MAGIの挿入点**：market-analyst / sell-recommender が信号（buy_signals / sell_signals）を出し、decisions に載せてUIへ流す**直前**。

```
market-analyst × N ─┐
                    ├→ ★MAGI独立検証 → decisions（検証結果付き）→ UI → ユーザー決裁
sell-recommender ───┘
```

- 検証対象は「これからユーザーが決裁する候補」。買いも売りも対象。
- MAGIを通過するまで、decisions は「決裁待ち」状態にしない（検証前の生信号をユーザーに出さない）。

## 2. MAGI独立検証機関の中身（4段）

ユーザーのジャッジ直前に、この4段が順に走る。

### 2.1 3審判（独立検証）
既存エージェントが出した推奨を、3つの観点から**互いを見ずに独立検証**する。各審判は「可否＋根拠＋確信度＋出典＋時点」を出す。

| 審判 | 検証する観点 | 参照する既存データ | モデル |
|---|---|---|---|
| MELCHIOR・1 | 業績（ファンダ）の裏付けはあるか | fundamentals / 財務数値 | Ollama |
| BALTHASAR・2 | 株価（テクニカル）の裏付けはあるか | technicals / 価格・出来高 | `[未確定]` 計算主体／LLMは解釈役か |
| CASPER・3 | 文脈（イベント・ニュース）の裏付けはあるか | news / disclosure / topics | Sonnet |

- 3審判は互いの結論を入力に取らない（プロンプト/関数を物理分離）。`[code判断：実装方法]`
- 反証専任は置かない。「割れること自体」が反対意見として機能する。
- 判定不能（データ欠損）は `verdict=na` として正直に出す。推測で埋めない。

### 2.2 防御層（ハルシネーション検出・遮断）
審判の判定と既存エージェントの推奨に含まれる**数値・出典・時点を、コードが機械的に照合**し、混入したハルシネーションを決裁前に遮断する。

この防御層は本要件の中核思想であり、MAGIの1段に留まらずシステム全層に効く。**詳細は独立章「第2H部：ハルシネーション防御（全層）」に定義する。** ここでは「審判の判定の直後に、コードが機械照合する関所がある」とだけ押さえる。

### 2.3 統合機構（判断しない）
3審判の見解を**並置し、割れ方を類型化するだけ**。総合スコアを出さない（`SCORE: NONE`）。

| 割れ方 | 解釈（推奨はしない） |
|---|---|
| 3審判一致 | 確信度高。ただし「全員同方向に誤った可能性」も併記 |
| 業績◯・株価✕ | 業績は良いが株価の勢いなし。タイミング尚早の疑い |
| 株価◯・業績✕ | 株価は動くが業績裏付けなし。需給先行の疑い |
| 文脈✕ | 数字は良いが上昇の文脈なし／織り込み済みの疑い |

割れ方の類型がこの4つで足りるかは `[未確定]`。

### 2.4 碇司令 GENDO（推奨役・決定しない）
- MAGIの出力**だけ**を根拠に、推奨と反対論拠（「反対するなら：」）を**必ず両方**生成する。
- MAGIにない新事実を創作してはならない（2.2でチェック）。
- 決定はしない。ユーザーの決裁材料として提示するだけ。

## 2H. ハルシネーション防御（全層・本要件の中核）

ハルシネーション対策は「MAGIの1段」ではなく、データ取得から決裁までの**全層に串刺しで効く独立した防御思想**である。原則は2つ。

> **原則A：数値はコードが照合した実データのみ。LLMに数値を生成・計算させない。**
> **原則B：ゼロ化は狙わない。混入を前提に、決裁の直前に必ず検出・遮断する。**

### 2H.1 防御が効く層（どこで何を守るか）

| 層 | 守る対象 | 防御の中身 |
|---|---|---|
| データ取得 | 取得値そのもの | 重要数値（株価等）は2ソースで取得・照合。不一致でフラグ。許容誤差 `[未確定]` |
| 既存エージェント出力 | 推奨に載る数値 | LLMが文中に出した数値が、コード取得の実データと一致するか照合 |
| 3審判の判定 | 根拠の数値・出典・時点 | 下記2H.2の3照合 |
| 碇司令の発言 | 碇が述べた事実 | MAGIにない事実を創作していないか照合（碇MAGI準拠） |
| 予測値（モデル生成） | bull/base/bear等 | 実データと区別。未照合バッジ。碇の根拠から除外 |

### 2H.2 機械照合の3本柱（コードが行う・LLMは関与しない）

1. **数値照合**：判定・推奨に出る各数値を、API取得の実データと突合。一致＝緑、不一致 or 出所不明＝赤＋ `unverified_claims` に列挙。
2. **出典実在確認**：根拠として挙げた出典（URL・開示・財務項目）が実在し、主張内容と整合するか。実在しない出典を引いていたら赤。
3. **時点照合**：各数値の as-of（取得時点）を保持し、古すぎる/時点が混在する場合に警告。「いつのデータか」を必ず添える。

### 2H.3 「分からない」を正直に出す（推測で埋めない）

- データ欠損で照合できない数値は、緑にしない。「未照合（データ欠損）」として赤系で明示。
- 審判が判定不能なら `verdict=na`。碇は「3審判のうちXが判定不能。確信を持てない」と述べる。
- 埋められない空欄を、それらしい値で埋めることを禁止する。

### 2H.4 碇MAGI準拠チェック（創作の遮断）

碇司令の推奨・反対論拠は、MAGIの出力（judge_verdict）の範囲内でのみ許される。範囲外の新事実（MAGIが言っていない数字・出来事）を碇が述べたら、`gendo_compliant=false` として赤フラグを立て、決裁前に検出する。

### 2H.5 決裁前ゲート（遮断の発動点）

- 検証フラグ（数値照合／信用性／碇MAGI準拠）に赤が1つでもあれば、UIの決裁ボタンの既定を「保留」に寄せる。
- 3審判が割れている時も既定を保留に。
- ユーザーは赤を承知の上で承認することは可能（最終決裁は人間）。ただし「未照合のまま承認する」ことが画面上で明示される。

### 2H.6 LLMにさせないことの線引き（実装の禁止事項）

- LLMに四則演算・スコア計算・比率計算をさせない。数値はすべてコードが計算・取得し、LLMには「読む」役だけを与える。
- LLMの出力に数値が含まれていたら、それは「LLMが言った数値」として疑い、コード照合を通すまで信用しない。
- 予測値（シナリオの目標株価等）はモデル生成と明示し、実データと同じ見せ方をしない。

## 4. UIとの接続（dashboard.html は実装済み・収束先）

MAGI検証結果は、完成済み dashboard.html のDOMに流し込む。クラス名は保つ。

| UI要素（実クラス） | 対応データ |
|---|---|
| `.gendo-ind .g-word`（推し/利確/撤退/要検討/静観） | decision の碇スタンス |
| `.magi-mini-dots`（一覧：3審判ミニ） | judge_verdict 3行 |
| `.magi-mini-state`（一覧：割れ方） | split_pattern.label |
| `.magi-jrow`（詳細：3審判リスト） | judge_verdict |
| `.magi-foot .mf-state` / `.mf-note`（SCORE: NONE） | split_pattern |
| `.cmd-rec` / `.cmd-counter`（碇の推奨/反対論拠） | commander_rec |
| `.magi-flag` ×3（数値照合/信用性/碇MAGI準拠） | verification |
| `.magi-btn` ×3（承認/否認/保留） | decision.status |

- 検証が終わるまで決裁ボタンは非活性。未照合 or 割れがある時は既定を「保留」に寄せる。
- 既存UIに残る旧前提（候補一覧の数値スコア `.mini-act-score`、予測グラフの未照合バッジ欠落、Track Recordのスコア相関）は実装時に改修。`[実装時改修]`

## 5. 状態遷移

```
（既存エージェントが信号生成）
  → MAGI検証中(verifying) → 検証完了(verified) → 決裁待ち(awaiting)
  → 承認(approved)/否認(denied)/保留(held)
  → approved → 発注リスト出力 → 手動発注済 → 保有
```

- MAGI検証中：UIはローディング、決裁ボタン非活性。
- エラー時：審判na→鼎立図を点線、碇は「Xが判定不能。確信を持てない」と述べる。
- API停止/予算超過：停止バナー、新規検証を止める。
