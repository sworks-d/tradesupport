## ⚠ STEP B で発生した STEP A レベルの変更点（重要）

STEP B のダッシュボード設計を進める中で、以下の方針が更新された：

1. **moomoo中心方針**：株価・出来高・残高・約定はmoomooから取得（一元化）。IR/開示はEDGAR/EDINET直接、ニュースはNewsAPI/RSSで独立性を確保。「データソースをmoomooに依存しすぎる」リスクは認識しつつ、運用シンプルさを優先。
2. **Phase 1から口座読み取り連携あり**：旧版では Phase 2 で broker MCP を導入予定だったが、moomoo の読み取り（残高・約定同期）は Phase 1 から実装。発注は引き続き手動（Tier 1）。
3. **レコメンドの売り対応を主役に**：買いと同等の重みで利確・損切りレコメンドを設計。旧版では「売り」は警告レベルだったが、投資の両輪として位置づけ直し。
4. **目標期間を銘柄ごとに設定**：30日固定ではなく、銘柄ごとに「中期3ヶ月／長期1年／中期-長期6ヶ月」等を持つ設計。グラフも目標期間を軸に描く。
5. **トピックスの透明性設計**：AIが判断に使ったニュースをユーザーが追跡できるよう、収集トピックスをダッシュボードに表示。重要度と影響先を明示。

詳細は STEP_B_FINAL.md を参照。

## 2. 投資戦略の構造（Core-Satellite）

```
ポートフォリオ全体（10万円）
├── コア戦略（メイン枠、80%目安）
│   ├── 中期V字回復戦略
│   └── 中期テーマ戦略
└── サテライト枠（20%目安）
    ├── 長期戦略（Phase 2で実装）
    └── 短期戦略（Phase 3で実装）
```

### 設計原則
- **主戦場は中期で固定**。市況で全戦略を切り替える「マーケットタイミング」は採用しない。
- **サテライト枠は最初から制度として存在する**。最初は空（コア100%）でもOK。
- **戦略エンジンはプラグイン化**。インターフェースを Phase 1 で定義、実装は段階的に追加。
- **データ取得層は時間軸非依存**で構築する（日足／週足／月足、財務、ニュース全て取る）。

### 「V字回復」「テーマ」の暫定定義
※詳細ロジックは STEP B で詰める

- **V字回復**：業績反転（赤字→黒字、減益→増益）＋ 株価底打ち反転 を合成した中期パターン
- **テーマ**：マクロトレンドや時事（AI、半導体、防衛、原油問題等）に紐づく中期上昇候補

### Stage に応じた支援内容の変化
ユーザーは Stage 1（保有ゼロ）から始まり、運用とともに育つ。エージェントの役割もこれに合わせて変わる。

| Stage | 状態 | 主な支援内容 |
|---|---|---|
| Stage 1 | 保有ゼロ | スクリーニング・発掘・初回ポートフォリオ構築 |
| Stage 2 | 数銘柄保有 | モニタリング＋追加発掘 |
| Stage 3 | 10銘柄〜成熟運用 | ポートフォリオ最適化、リバランス |

ツールは Stage 1 から始めて、Stage 2-3 に育つ前提で設計する。

## 6. ブローカー：moomoo OpenAPI

### 採用理由
- 米国株＋日本株の両方で個人が無料でAPI自動売買可能（2026年3月以降日本対応）
- macOS でも OpenD が動作（Windows必須の auカブコムkabuステーションと違う）
- Python公式SDK、moomoo証券公式の日本語ドキュメントあり
- 「画面に張り付く投資」から「プログラムに任せる投資」を公式が推している

### データの一元化方針（STEP B で確定）

moomoo を**実運用データの単一ソース**とする：

| データ種類 | ソース | 理由 |
|---|---|---|
| 株価・出来高（リアルタイム） | moomoo | 実約定するブローカーの提示価格と整合 |
| 保有銘柄・残高 | moomoo | 実口座と完全同期 |
| 約定履歴 | moomoo | 自動取り込みで手入力不要 |
| IR・開示（米） | SEC EDGAR | 一次情報、moomoo経由だと加工される |
| IR・開示（日） | EDINET / TDnet RSS | 同上 |
| ニュース | NewsAPI / 各種RSS | 独立性、複数ソース照合 |
| 過去価格・財務（補助） | yfinance / J-Quants | バックテスト・スクリーニング用 |

moomoo のAI機能（AIチャート予測、パターン検出等）は **API で取れないため使わない**。当ツールが独自に分析する。

### 注意点
- OpenD（中継プログラム）の常時起動が必要
- 米国株 Lv2 等の一部リアルタイムデータは別途有料
- PTS（夜間取引）はAPI経由で非対応
- 日本株のAPI機能は記事によって表記揺れあり、実装時点で公式ドキュメント要確認

### 自動売買のスタンス
3段階で進める（STEP B で Tier 1 内に「読み取り連携あり」を追加）：

| Tier | 方式 | 着手時期 |
|---|---|---|
| **Tier 1** | 分析のみ、発注は手動、**約定・残高は自動同期** | Phase 1〜 |
| **Tier 2** | AIが発注リスト出力、UIでワンクリック発注 | Phase 2〜 |
| **Tier 3** | 完全自動売買（moomoo OpenAPI 経由） | Phase 3 以降 |

判断品質に確信が持てるまで発注は手動。Tier 1 のフリクションが**最終人間チェック**として機能する。

ただし**読み取り連携（残高・約定の自動同期）は Phase 1 から実装**することで、ユーザーの手入力負担を減らす。発注後の手入力は実運用で必ず破綻するため、ここは早めに自動化する。

### 重要な設計判断

**1. MCPをデータアクセスの中核に据える**
- エージェントは MCP ツールを呼んでデータを取る
- データソース変更時もエージェント側に影響しない

**2. ベース選定の整理（重要）**
「ai-hedge-fundをベースに」という当初の判断は撤回した。実態：
- **基本は自作**（戦略やUIがカスタム性高いため）
- **F6（IR分析）のみ西岡氏のib-sec-mcp パターンを参考**
- 既存OSSは適材適所で**ライブラリとして部分採用**
- 詳細は「機能 × リポジトリマッピング」参照

**3. Hot Path / Cold Path 分離**

| Path | 担当 | LLM |
|---|---|---|
| Cold | News要約、決算整形、定型処理 | Ollama |
| Hot | 投資判断、IR深掘り分析 | Claude Sonnet 4.6 |
| Critical | 最終判断、重大リスク評価 | Claude Opus 4.7（必要時） |

これは月5,000円の予算を守る最重要設計判断。

- 朝バッチで売り推奨・買い推奨・トピックスがダッシュボードに表示される

- ペーパー運用で4週間以上の稼働実績
- 売り推奨の的中率が許容範囲（具体的なしきい値は STEP C で決定）

## 14. STEP C で詰めるべき論点（STEP B 完了時点）

ダッシュボードの設計を通じて、技術設計レベルで詰める必要が明確になった論点：

### 機能ロジック
1. **V字検出ロジックの定量的しきい値**：業績反転と株価底打ちの組み合わせ条件
2. **テーマ戦略の検出ロジック**：マクロイベントの自動検出と銘柄紐付け
3. **売りスコアの算出ロジック**：利確スコアと損切りスコアの計算式
4. **シナリオ進捗の算出方法**：定量的に「何%達成」を計算する方法
5. **目標期間の決定ロジック**：銘柄ごとの目標期間をどう決めるか（戦略カテゴリで分類）
6. **初回10万円の配分ロジック**：Core-Satellite の比率と銘柄選定

### システム設計
7. **MCPツールの分割粒度**：どこまで細かく分けるか
8. **エージェント間のメッセージ受け渡しスキーマ**：型定義
9. **データモデル（ERD）**：decisions, portfolio, topics, analysis_logs 等のテーブル定義
10. **moomoo OpenD との接続管理**：常時起動、再接続戦略
11. **トピックスの分類タグ体系**：マクロ／業界／個別の自動分類ロジック
12. **重要度判定ロジック**：トピックスをどう「重要・中・低」に分類するか
13. **Hot Path / Cold Path の判定基準**：どのタスクがどのLLMに行くか

### 運用設計
14. **朝バッチの実行タイミングと処理内容**
15. **手動発注後の同期タイミング**（リアルタイム or 定期）
16. **緊急停止と再開のフロー**
