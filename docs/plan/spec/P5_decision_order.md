# P5 決裁・発注 — フェーズ設計＋タスク設計

**フェーズの役割**：人間が承認/否認/保留を決め、承認は Tier1（手動発注）として moomoo で発注→記録→保有化。
**全体ゴール寄与**：自動売買せず、人間の決裁を最終とする（不変原則2/5）。検証フラグが揃わなければ既定保留。
**前からの引き継ぎ**：P4の検証済み decision（status=awaiting、既定decision付き）。**次への引き渡し**：
決裁結果（status更新）→発注リスト→positions（→P6評価）。
**フェーズのハルシネ防止方針**：R6 未照合/割れは既定保留（人間が赤承知で承認は可能・画面に明示）／R1 発注数量はサイジングのコード値。

> 状態：✅ / 🟡 / ❌

### P5-1 決裁UI配線  〔🟡 表示のみ〕
- 全体ゴール：承認/否認/保留を人間が押し、結果を保存。
- 前からの引き継ぎ：decision（status=awaiting、検証フラグ、碇推奨、サイジング、既定保留）。
- 目的：ボタン押下→`decision.status` 更新（approved/denied/held）＋理由記録。
- 実装：FastAPI `POST /api/decisions/{id}`＋UI（決裁ボタン onClick）。未照合/割れは既定「保留」を選択状態に。
- 次への引き渡し：status=approved の decision（→P5-2）／denied・held は decision_log。
- ハルシネ防止：R6 既定保留／承認時に「未照合のまま承認」を画面明示／碇の反対論拠を読む動線。
- 受入：押下で status 保存・画面反映。

### P5-2 発注リスト出力（Tier1手動）  〔❌ 未〕
- 全体ゴール：承認分を moomoo 手動発注できる形に出力。
- 前からの引き継ぎ：status=approved の decision＋サイジング（株数・金額）。
- 目的：発注リスト（銘柄/数量/想定価格/メモ）を画面/CSVで出力。**自動発注はしない**（Tier1）。
- 実装：発注リスト生成（FastAPI/ui）。moomoo発注APIは持つが Tier1 では使わず手動。
- 次への引き渡し：発注リスト（人間が moomoo で発注）→P5-3で記録。
- ハルシネ防止：R1 数量はサイジングのコード値のみ／R7 承認decision以外は出さない。
- 受入：承認→発注リストに正しい数量で出る。

### P5-3 発注記録→保有化  〔❌ 未〕
- 全体ゴール：実際の発注を記録し、保有(positions)に反映。
- 前からの引き継ぎ：手動発注の結果（or moomoo約定）。
- 目的：発注記録を入力/同期し、decisionをholding化、portfolioに反映。
- 実装：`brokers/moomoo.py`（約定/positions取得）＋記録UI。同意②＋OpenD後に実データ。
- 次への引き渡し：holding（取得単価・数量）（→P1-10/P6評価、U保有パネル）。
- ハルシネ防止：R1 取得単価/数量は moomoo 実値／R2 約定時点を保持。
- 受入：発注→保有パネルに実建玉が出る（moomoo接続後）。
