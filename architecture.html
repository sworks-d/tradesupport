1. システム全体図

図の読み方： オレンジ実線 = moomoo関連のデータフロー（一元化方針）。 紫 = MCP（エージェント↔ツール）。 赤 = LLM呼び出し。 灰色破線枠 = Phase 2 以降の追加要素。 緑枠付き = STEP B で確定した新規／前倒し要素。

2. データフロー：朝バッチの典型シナリオ

時刻 処理 担当
05:00 APScheduler が朝バッチを起動 FastAPI / Scheduler
05:01 moomoo OpenD から保有銘柄・残高・約定を取得 → portfolio テーブル更新 broker_read
05:02 NewsAPI / RSS から過去24時間のニュース取得、AIで分類・重要度判定 → topics テーブル news + Ollama
05:05 screening-agent が V字+テーマで287銘柄から候補10-20件抽出 screening + Sonnet
05:10 market-analyst × N が候補銘柄を並列で詳細分析（ファンダ・テクニカル・ニュース） fundamentals/technicals/news + Sonnet
05:20 sell-recommender が保有銘柄を分析、利確スコアと損切りスコアを算出 market_data/news + Sonnet
05:25 レコメンドを decisions テーブルに保存、トピックスの影響先を紐付け SQLite
05:30 朝バッチ完了。ユーザーが起きたタイミングでダッシュボードを開けば最新表示 UI
06:30 あなたが起床、ダッシュボードを開く。売り買いレコメンドを確認、moomooで手動発注 YOU
06:45 発注後、moomoo OpenD 経由で約定が自動同期、portfolio テーブルが最新化 broker_read
任意 X発言・記事URLを「手動投入」に投げ込み、即時解釈（manual-input-analyst） Sonnet
朝バッチは LLM 呼び出しが集中するタイミング。Hot Path（Sonnet）と Cold Path（Ollama）の振り分けが月¥5,000の予算遵守の鍵。 ニュース要約・トピックス分類は Ollama、判断系のみ Sonnet/Opus を使う。

5. データモデル（Phase 1 主要テーブル）

テーブル 役割 主要カラム（抜粋）
decisions レコメンド履歴（買い/売り/利確/損切り）。的中率算出に使用 id, date, ticker, action, score, scenario, expected_return, actual_return, hit_or_miss
portfolio 保有銘柄。moomoo と同期 ticker, buy_date, buy_price, qty, target_date, target_pct, strategy_category, status
topics 【NEW】 収集ニュース・IR・X発言。AI分類済み id, time, category, importance, headline, summary, source_url, affected_tickers, impact_text
scenarios 各レコメンドのシナリオ（強気/ベース/弱気）と進捗 decision_id, scenario_type, target, prob, current_progress
analysis_logs エージェント実行ログ（trace） id, agent, started_at, ended_at, input, output, tokens, cost
cost_logs API消費追跡（日次・月次予算管理） date, model, tokens_in, tokens_out, cost_usd, cost_jpy

6. ユーザーの関与ポイント

場面 あなたがやること 頻度
初期セットアップ moomoo口座開設、各APIキー取得、Anthropic/J-Quants/EDINET/NewsAPI登録、 .env 設定、Ollama インストール 初回のみ
朝のレビュー ダッシュボードを開き、売り買いレコメンドを確認 → 採用判断 毎朝 3-5分
moomoo発注 採用したレコメンドの指値・数量をmoomooアプリでコピペ入力 取引日のみ
深掘り 気になる銘柄の詳細パネルを開いて読み込む / トピックスのソースを開く 任意
手動投入 X発言・記事URLを「手動投入」に貼り付け、即時解釈をリクエスト 速報時
緊急停止 ~/.trading-agent/HALT ファイル作成で全停止 緊急時のみ
週次振り返り 週次レポート画面（STEP B 続編）で1週間の振り返り 週1回
Phase 1 の重要設計判断： 「手動発注 + 自動同期」という中間形態を採用した。完全自動売買は Phase 3、完全手動入力は実運用で必ず破綻する。 「moomooアプリで発注 → 約定は自動でツールに反映」のハイブリッドが、ユーザーの最終チェックを担保しつつ、ツールが常に最新データを持てる落とし所。
